# AGENTS.md

## Project overview

QuickCrawl is a TypeScript web-crawling API and web UI built with Node.js 24,
pnpm 10, Hono, Vitest, Rolldown, Tailwind CSS v4, Cheerio, and Turndown.

Read the relevant documentation before making substantial changes:

- `README.md` — product overview and usage
- `docs/ARCHITECTURE.md` — system structure and workflow design
- `docs/DEVELOPMENT.md` — development and extension instructions
- `docs/API.md` — public HTTP contract
- `docs/DECISIONS.md` — architectural decisions
- `CONTRIBUTING.md` — code, test, and commit conventions

## Commands

Use pnpm. Do not introduce npm, Yarn, or Bun lockfiles.

```bash
pnpm install
pnpm run dev
pnpm run typecheck
pnpm test
pnpm run build
pnpm run build:css
```

Before considering a code change complete, run:

```bash
pnpm run typecheck
pnpm test
pnpm run build
```

Run focused Vitest tests while iterating when appropriate.

## Repository structure

- `src/index.ts` — Hono application and API route wiring
- `src/server.ts` — local Node.js server entry point
- `src/config.ts` — validated runtime configuration and application metadata
- `src/routes/` — UI routes
- `src/ui/` — Hono JSX components and browser-side UI code
- `src/services/` — business services and caching decorator
- `src/lib/` — shared cache, logging, errors, and rate-limiting utilities
- `src/middleware/` — HTTP middleware
- `src/workflow/` — generic workflow contracts
- `src/workflows/crawl/` — crawl pipeline, tasks, types, guards, and URL safety
- `public/styles.css` — generated Tailwind output
- `docs/` — API, architecture, development, and decision documentation

Tests are generally colocated with the source using `*.test.ts` or
`*.test.tsx`.

## Architectural constraints

### Crawl workflow

The crawl pipeline uses discriminated unions and explicit typed transitions:

1. `initial`
2. `fetched`
3. `metadata_extracted`
4. `parsed`
5. `cleaned`
6. `completed`

When adding or changing a workflow stage:

- Update `src/workflows/crawl/types.ts`.
- Keep each task's input and output types explicit.
- Add the task under `src/workflows/crawl/tasks/`.
- Export it through the task index.
- Compose it explicitly in `createCrawlWorkflow.ts`.
- Preserve `AbortSignal` propagation.
- Add tests for the transition and failure behavior.
- Update architecture documentation when the pipeline changes.

Do not weaken workflow types with `any`, optional catch-all fields, or unchecked
casts.

### Error handling

Public service and API results use discriminated unions.

- Preserve structured `CrawlError` values.
- Translate failures at the appropriate service or HTTP boundary.
- Do not expose internal exception details in API responses.
- Use the existing structured logger rather than `console.log`.

### URL and network safety

Crawling user-provided URLs creates an SSRF risk.

- All crawl targets must pass through the existing URL-safety validation.
- Continue to allow only HTTP and HTTPS.
- Do not permit credentials in URLs.
- Do not weaken blocking for localhost, private, link-local, reserved, multicast,
  or otherwise non-public addresses.
- Add security-focused tests for changes to URL parsing, DNS resolution,
  redirects, or fetching behavior.
- Preserve cancellation, timeouts, and bounded retry behavior.

### Rate limiting and proxies

- Treat forwarded client IP headers as untrusted unless `TRUST_PROXY` is enabled.
- Do not change proxy or rate-limit behavior without tests.
- Document changes to related environment variables.

### Configuration

- Validate runtime configuration in `src/config.ts`.
- Add new environment variables to `.env.example`.
- Document user-facing configuration in `README.md` and relevant docs.
- Never commit `.env` files, credentials, tokens, or production secrets.

### UI and generated CSS

- Edit Tailwind source and JSX under `src/ui/`.
- `public/styles.css` is generated by `pnpm run build:css`.
- If UI classes or source styles change, regenerate the compiled stylesheet.
- Keep the UI usable without relying on a separate frontend server.
- Preserve accessibility and responsive behavior.

## Code conventions

Follow `CONTRIBUTING.md`. In particular:

- Keep TypeScript strict.
- Prefer precise types and discriminated unions.
- Use `unknown` instead of `any`.
- Use `import type` for type-only imports.
- Respect `verbatimModuleSyntax`.
- Keep modules focused and dependencies flowing through clear interfaces.
- Prefer existing utilities and patterns before introducing new abstractions.
- Avoid unrelated refactors in narrowly scoped changes.

Match the formatting and naming of surrounding code. Do not add a formatter,
linter, dependency, or framework without explicit justification.

## Testing expectations

Add or update tests for behavioral changes. At minimum, cover:

- Successful behavior
- Expected error behavior
- Boundary and validation cases
- Cancellation or timeout behavior when relevant
- Security cases for URL fetching and proxy-derived identity
- Cache and rate-limit edge cases when those modules change

Avoid tests that depend on live public websites or nondeterministic external
network access. Inject or mock network and DNS behavior where practical.

## Documentation contract

`docs/INDEX.md` defines the canonical owner for each documentation topic. Keep
summaries in other documents short and link to the canonical source instead of
copying detailed instructions.

Update documentation in the same change when modifying:

- Public endpoints or response shapes → `docs/API.md`
- Architecture or workflow stages → `docs/ARCHITECTURE.md`
- Setup, commands, or development practices → `docs/DEVELOPMENT.md`
- Major user-facing capabilities or configuration → `README.md`
- Significant technical decisions → `docs/DECISIONS.md`
- Released behavior → `CHANGELOG.md`

Keep examples consistent with the implementation.

## Change discipline

- Inspect the existing working tree before editing.
- Preserve unrelated user changes.
- Do not rewrite generated files manually.
- Do not perform deployments, create releases, or modify external services
  unless explicitly requested.
- Do not commit or push unless explicitly requested.
- Use Conventional Commits when asked to create a commit.
